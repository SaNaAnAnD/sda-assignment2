Transactions and sessions are keyed by customer so that all events for one customer land in the same partition and stay ordered — required by the rolling-statistics logic in the fraud scorer. Gateway responses are keyed by bank because the health monitor aggregates per bank over a tumbling window.

Sample Data

Generated by generate_reference_data.py, seeded so the dataset is reproducible.

File	Rows	Contents
customer_persona.csv	5,000	Segment, 30-day rolling mean and SD of spend, home location, KYC status
merchant_master.csv	5,000	MCC, risk tier, onboarding date, channel, settlement cycle
device_registry.csv	7,907	One row per customer–device pair with last-seen date
acquiring_banks.csv	5	Baseline success rate and latency per bank (simulation parameters)

Why not Faker. The fraud rule from Assignment 1 flags a transaction when the amount exceeds that customer's 30-day rolling mean by more than 3 standard deviations. This only works if streamed amounts are drawn from the same per-customer distribution stored in the reference data. Independently generated values would make the test meaningless.

Realism controls built in:

Five customer segments with spending means from ₹180 to ₹18,000
Merchant risk tier derived from MCC, escalated for merchants under 90 days old
4.5% of devices dormant beyond the 90-day threshold, so the device leg of the fraud rule has genuine positive and negative cases
Unequal routing weights across the five acquiring banks
Injected Scenarios

Without deliberate anomalies the downstream consumers would run correctly and detect nothing.

Fraud — 1.5% of transactions. Amount set 3.5–8.0 SD above the customer's mean; 85% on an unseen device, 60% geo-mismatched, 70% at a high-risk merchant. The device probability is below 100% deliberately: since the rule is a conjunction, roughly 15% of injected anomalies will not be flagged, giving a realistic recall figure rather than 100%.

Gateway degradation. Axis Bank drops from 96.5% to 71% success and 280 ms to ~1,450 ms latency at T+180s, holds for 240s, then recovers. Failure codes shift toward ISSUER_UNAVAILABLE and SYSTEM_MALFUNCTION during the window. This is the scenario the Payments Operations Manager persona acts on.

Both are parameterised in sim_config.json.

Running It

Prerequisites: Docker with Kafka and Zookeeper, Python 3, pip install kafka-python

Create the topics:

bash
for t in transactions user_sessions gateway_status; do
  kafka-topics.sh --bootstrap-server localhost:9092 --create --topic $t --partitions 3 --replication-factor 1
done
for t in merchant_ref customer_persona; do
  kafka-topics.sh --bootstrap-server localhost:9092 --create --topic $t --partitions 1 --replication-factor 1
done

Load the reference topics (one-shot):

bash
python3 persona_loader.py
python3 merchant_loader.py

Start the streams in three terminals, in this order — gateway_producer.py consumes from transactions, so it has no input until the first is running:

bash
python3 txn_producer.py              # terminal 1
python3 app_telemetry_producer.py    # terminal 2
python3 gateway_producer.py          # terminal 3

Run for at least 8 minutes so the full outage cycle completes. Ctrl+C to stop; each producer prints a summary.

Validation
Anomaly rate: 466 / 31,671 = 1.47% against 1.50% configured
Outage magnitude: degradation covered 240s of a 599s run (40.1%). Predicted Axis cumulative success = (0.599 × 96.5%) + (0.401 × 71%) = 86.3%; observed 86.0%
Routing weights: observed shares match configured weights within 0.4 pp
Stream correspondence: the transaction producer ran 34s longer than the gateway producer; at 50/sec that accounts for ~1,700 events, against an observed difference of 1,748 — consistent with a strict one-to-one relationship
Partition skew

transactions splits 10,563 / 10,554 / 10,554 (spread under 0.1%) across 5,000 distinct customer keys. gateway_status splits 13,772 / 7,257 / 8,894 — nearly 2:1 — because there are only five bank keys to hash into three partitions. Both are correct; the skew is the cost of keying by the field the consumer needs to aggregate on.

Limitations
Single broker, so replication factor is 1 and there is no fault tolerance
The _injected_anomaly field on each transaction is ground truth for evaluation and has no production equivalent
Customer baselines are static; Assignment 1 specifies a nightly refresh not simulated here
The outage is scripted rather than emergent
Injected frauds are independent, whereas real fraud often occurs in bursts against one compromised account — velocity-based detection cannot be evaluated on this dataset
